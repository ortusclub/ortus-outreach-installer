# FG Master sheet — design

Date: 2026-08-07
Status: proposed
Owner request: Sam / Mickey (via Antonio)

## Problem

The Follower Growth campaign currently writes only machine-shaped tabs: `FG Invites`
(one row per target × operator, queued/invited ledger), `FG Budgets`, and per-run
`FG YYYY-MM-DD` list tabs. Nobody can open the FG sheet and answer "who do we know,
through which accounts, and have we invited them yet?".

Meanwhile the team answers that question by hand in a different spreadsheet
(*Project Internal Template FUNNEL_I* → tabs `Marketing Leaders 1st Degree
Connections` / `LinkedIn Accounts Status`), typing `Invited` and the sending
account per person. That manual sheet is the pattern to reproduce — not the file
to write into.

## What we build

One new tab, **`FG Master`**, in the FG spreadsheet the app already owns. It is
the whole warm network as a flat human-readable table, generated from the
Connections DB, with the invite ledger stamped onto each person's row.

### Columns

| # | Column | Source |
|---|---|---|
| 1 | First Name | `contact.firstname` |
| 2 | Last Name | `contact.lastname` |
| 3 | Job Title | `contact.jobtitle` |
| 4 | Company | `contact.company` |
| 5 | Geo | `city, state, country` (blanks dropped) |
| 6 | LinkedIn URL | `contact.linkedinbio` |
| 7 | Member ID | `contact.linkedin_membership_id` (often blank — see Identity) |
| 8 | Connected Accounts | `warmVia` joined with `", "` — every operator account holding this person as a 1st-degree connection |
| 9 | Invited | `Invited` once an invite is sent, else blank |
| 10 | Invited At | `YYYY-MM-DD HH:mm UTC` |
| 11 | Invited By | sending account email |

Columns 1–8 are regenerated by a build; 9–11 are stamped by runs and preserved
across rebuilds (see Rebuild).

### Population

Non-DNC contacts with at least one warm account (`hasWarm`), from the same
`getAnnotated()` join the FG target builder already uses
(`src/connections/search-service.js`). No new data source, no new credential.

Current size: **278,979 rows** (49,465 of them connected through more than one
account) × 11 columns = ~3.1M cells. Sheets' hard cap is 10M cells per
spreadsheet, so this fits, but `FG Master` will be by far the largest object in
that file. Rows without a LinkedIn URL are skipped — they can never be invited
and cannot be keyed for stamping.

No role filter by default: the sheet is the whole network. The build endpoint
accepts an optional `roles` keyword list (same semantics as the FG builder's
title chips) for a narrower rebuild, off unless passed.

## Architecture

### Build — `fgWriteMaster` (new Apps Script action)

`fgWriteList` replaces a tab in a single `setValues`, which cannot carry 279k
rows in one POST. `fgWriteMaster` takes `{ tab, header, rows, mode }` where
`mode: 'replace'` clears the tab and writes the header, and `mode: 'append'`
appends a chunk. The app posts the header with `replace`, then ~5k-row chunks
with `append` (~56 POSTs, sequential, each well inside the Apps Script 6-minute
execution limit).

App side: `buildMasterRows()` in `src/connections/fg-master.js` (pure, testable)
turns annotated records into `FG_MASTER_HEADER`-order string rows;
`writeFgMaster()` in `fg-sync.js` does the chunked POST loop; an
`/api/fg/master/build` route runs it with progress in the same
`_fgSend`-style status object the FG UI already polls, plus a button in the FG
section of the UI.

Build is idempotent: re-running rewrites the tab from scratch.

### Stamp — inside `fgMarkInvited_`

Every send path in the codebase — local send (`server.js:2682`), team launch
(`server.js:3128`), cloud reconcile (`server.js:2768`,
`services/fg-roster/reconcile.js:86`) — already funnels through
`markFgInvited()` → the Apps Script `fgMarkInvited_` action. That is the single
choke point, so the master stamp goes there and **no JS call site changes**.

`fgMarkInvited_` gains: after flipping `FG Invites` rows, read only the
`LinkedIn URL` and `Member ID` columns of `FG Master` (two single-column
`getValues` — ~2MB, not the 3.1M-cell grid), build a key→row index, and write
`Invited` / `Invited At` / `Invited By` for the ≤30 rows this call covers.
Missing tab → no-op, so a deployment that hasn't built the master yet is
harmless.

### Identity

`linkedin_membership_id` is null for a large share of contacts, and cloud list
runs invite by URL. So the stamp matches on **Member ID when present, else
normalised LinkedIn URL** (same rule as `inviteIdentity()` in `fg-list.js`:
lower-cased, scheme/`www`/trailing-slash/query stripped).

To make the URL available at stamp time, `fgMarkInvited` accepts an optional
`invited: [{ memberId, url }]` alongside the existing `memberIds` array.
`invitedWritebackFromLeads()` (`src/connections/fg-cloud-launch.js`) and the
team-launch writeback populate it from the leads they already hold; the local
send path keeps sending `memberIds` only. `memberIds` stays authoritative for
the `FG Invites` flip, so existing behaviour is unchanged.

### Rebuild without losing the ledger

A rebuild regenerates columns 1–8 from the DB and would blank 9–11. Before
writing, the build reads `FG Invites` (already available via `getFgState()`) and
backfills `Invited` / `Invited At` / `Invited By` from every row with
`Status === 'Invited'`, keyed by the same Member-ID-else-URL identity. This also
means **the first build arrives with all historical invites already stamped**,
not an empty ledger.

`FG Invites` therefore stays the source of truth for what was sent; `FG Master`
is a generated view of the network with that truth joined in.

## Error handling

- A failed chunk POST aborts the build with the chunk index in the status object;
  re-running rebuilds from scratch (no partial-state repair path — the build is
  cheap to redo and the tab is machine-generated).
- The master stamp inside `fgMarkInvited_` is wrapped so a failure (missing tab,
  malformed header) logs and returns normally — an invite must never be lost
  because a reporting tab misbehaved.
- Contacts with no LinkedIn URL are dropped at build time and counted in the
  build result.

## Testing

- Unit (`node --test`): `buildMasterRows()` — column order, geo joining, multi-
  account `Connected Accounts`, URL-less contacts dropped, DNC excluded.
- Unit: the backfill join — Member-ID match, URL-fallback match, no-match left blank.
- Unit: chunking — row counts and `mode` sequence for a given chunk size.
- Manual: build against the real FG sheet, confirm row count matches
  `getConnectionsStats()`, run one FG invite, confirm that person's row shows
  `Invited` / time / account.

## Out of scope

- Writing anything into Sam's FUNNEL_I spreadsheet. We reproduce the system in
  the app's own sheet, as agreed.
- `LinkedIn Accounts Status`-style per-account × month "Done" grid.
- Any change to how targets are selected or sent.
