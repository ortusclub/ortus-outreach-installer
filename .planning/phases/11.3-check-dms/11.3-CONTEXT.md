<domain>
## Phase Boundary

Deliver a new **manual, on-demand `check_dms` mode** that scans LinkedIn DMs for replies to prospects previously messaged by the selected GoLogin profile(s), and surfaces new replies in the dashboard (Replies panel) + writes back to the Google Sheet.

**In scope:**
- New "Check DMs" button inside the existing Campaign section (no tab-framework dependency — that's original Phase 12)
- Per-profile scoping: scan only rows where `Message="sent"` AND `Account Used` matches the running profile
- Voyager API primary detection path + DOM scrape fallback
- Per-profile `last_check_at` watermark for "only new replies since last run"
- Replies panel in the dashboard with prospect name, snippet, timestamp, "Open Thread" (external browser)
- Sheet writeback: auto-add `Reply`, `Reply At`, `Reply Preview` columns; non-destructive
- Clear error surfacing when Voyager fails and fallback is attempted
- Mutex: cannot run alongside a campaign (both need the same browsers)

**Out of scope (explicitly deferred — see `<deferred>` block):**
- Full-thread text fetch beyond inbox snippet
- Auto-responder filtering
- Auto follow-up on replies
- Email/push notifications
- "Handled in our app" read-state tracking (let LinkedIn own read-state)
- Tab framework (original Phase 12)

</domain>

<decisions>
## Implementation Decisions

### Trigger model
- **Manual, on-demand.** Button in the Campaign section labeled "Check DMs". No cron, no auto-run after send, no background monitor.
- Rationale: operators treat this as a "morning ritual" — conscious triage, not passive notifications.

### Per-profile scoping
- Each GoLogin profile only checks its own sent DMs. Scan rows where:
  - `Message = "sent"` AND
  - `Account Used = <running profile name>`
- Multi-profile: operator can select multiple profiles before clicking; iterate sequentially (reuse the same `ensureOpen` pattern from `src/campaign.js`).
- No cross-contamination: Antonio's profile never checks Patricia's rows.

### Detection method
- **Primary:** LinkedIn Voyager API `GET /voyager/api/messaging/conversations` — authenticated JSON call via the same pattern `getVoyagerDegree` uses at `src/linkedin/helpers.js:112`.
- **Fallback:** DOM scrape of `linkedin.com/messaging/` inbox list — triggered when Voyager returns non-2xx or structurally invalid payload.
- Rationale: Voyager is faster, no selector fragility, already battle-tested in the codebase. Scrape is the escape hatch.

### Match logic (LinkedIn conversation → sheet row)
- Fuzzy match conversation participant's **first + last name** (case-insensitive, trim whitespace) against `firstName` + `lastName` columns on candidate rows (already filtered to "this profile's sent DMs").
- Tiebreak by LinkedIn URL if present on the sheet row.
- Unmatched conversations: log (for debugging) but do NOT surface in the Replies panel (they're likely personal contacts, not campaign leads).

### Delta semantics — "only new replies since last run"
- Persist `last_check_at` per GoLogin profile in a new local state file: `{ORTUS_DATA_DIR}/data/check-dms-state.json`, keyed by profile name.
- On each run: only surface replies where LinkedIn's last-message timestamp > that profile's `last_check_at`.
- Update `last_check_at` to the **run's start time** only AFTER a successful scan completes (don't advance on partial failure — operator must be able to retry and not lose replies).
- First-ever run per profile (no watermark yet): show ALL replies.

### Output — UI (dashboard)
- New "Replies" panel in the Campaign section (vanilla JS + CSS, served via Express static), populated when the check finishes.
- Each row shows: prospect name, last message snippet (~80–100 chars), timestamp (relative: "2h ago"), "Open Thread" button.
- "Open Thread" opens `https://www.linkedin.com/messaging/thread/{threadId}/` via **`shell.openExternal`** (system browser — NOT inside Electron). Keeps LinkedIn's cookie state intact.

### Output — sheet writeback
- New auto-added columns via the existing `ensureTrackingColumns` helper at `src/sheets-writer.js:67`:
  - `Reply` — `"yes"` or empty
  - `Reply At` — ISO timestamp
  - `Reply Preview` — first ~100 chars of the reply
- **Non-destructive**: if row already has `Reply="yes"` from a prior run, do NOT overwrite.
- Writeback goes through the existing Apps Script webapp POST pattern (no new Apps Script endpoint, but TRACKING_COLUMNS + FIELD_MAP in `google-apps-script.js` need extending).

### Error handling
- If Voyager returns non-2xx: log status + URL, attempt DOM scrape fallback.
- If fallback also fails: surface error in Replies panel ("Check DMs failed for profile Antonio: Voyager 429; fallback also failed. Watermark NOT advanced — retry later.").
- Do NOT advance `last_check_at` on partial/complete failure.

### Rate limiting
- Apply existing per-action delays if signs of throttling appear (reuse the pattern from campaign.js's inter-lead delays).
- One API call per page of conversations; volumes per profile expected to be low (< 5 pages).

### Mutex with campaigns
- `/api/check-dms/start` MUST reject (409) if `campaign.running === true`.
- `/api/campaign/start` MUST reject (409) if `checkDms.running === true`.
- UI: Check DMs button disabled while a campaign runs, and vice versa.

</decisions>

<specifics>
## Specific Ideas

### Exact endpoint (primary)
- `GET https://www.linkedin.com/voyager/api/messaging/conversations?keyVersion=LEGACY_INBOX&q=search&...`
  - Plan 11.3-01 (research/fixture capture) MUST verify the exact query shape. LinkedIn has multiple variants (`q=search`, `q=participants`, newer `/messaging/conversationsV2`). Pick the one that returns "all conversations sorted by last-message time" without requiring a specific participant filter.

### Exact thread URL format
- `https://www.linkedin.com/messaging/thread/{threadId}/`
- `threadId` comes from the Voyager payload's `entityUrn` (e.g., `urn:li:fs_conversation:2-ZDdkM2M0MDUt...`). Strip the prefix to `2-ZDdkM2M0MDUt...`.

### State-file shape
```json
{
  "Antonio": { "last_check_at": "2026-04-23T08:00:00.000Z" },
  "Patricia": { "last_check_at": "2026-04-22T14:30:00.000Z" }
}
```

### Dashboard polling
- New `/api/check-dms/status` endpoint, polled every 2s by the UI while a scan is running. Returns `{ running, currentProfile, repliesFound, errors }`.
- Separate from `/api/campaign/status` — they never run simultaneously (mutex), but the polling loops are independent.

### Multi-profile iteration
- Operator selects `[Antonio, Patricia]` and clicks Check DMs:
  1. Launch GoLogin profile "Antonio" → run Voyager scan → close profile
  2. Launch GoLogin profile "Patricia" → run Voyager scan → close profile
  3. Aggregate results in Replies panel (grouped by profile)

</specifics>
