## CSS conventions to obey

From `public/css/style.css` (inventory shows ~50 class prefixes):

- `.section` — outer container for collapsible sections in the Campaign area
- `.section-header` / `.section-body` — header + collapsible body
- `.pill` / `.chip` — status indicators
- `.btn` / `.btn-primary` / `.btn-secondary` — existing button classes
- Monochrome palette only: `#fff`, shades of `#ccc` → `#333`, `#000`. Per memory: NO color backgrounds, NO new fonts.
- Use existing CSS variables (`--bg`, `--fg`, `--border`) — don't introduce new ones

## Anti-patterns to avoid

| Don't | Because |
|---|---|
| Introduce `innerHTML` for LinkedIn-sourced text | XSS — participants can put `<script>` in their name/message |
| Reuse the `pollStatus` function for Check DMs | Coupling — Check DMs state is independent; sharing one poller breaks both when either changes |
| Add `colored` backgrounds to the Replies panel | User explicitly prefers monochrome; breaks command-deck aesthetic |
| Write new auth code for the Voyager fetch | `getVoyagerDegree` auth already works; copy it byte-for-byte |
| Invent a new state-file location | `dataPath()` in `src/paths.js` is the single source of truth |
| Add the Replies panel as a separate tab | Tab framework is Phase 12+; Replies panel lives INSIDE the Campaign section per CONTEXT |
| Duplicate `ensureOpen` / `closeSession` in check-dms.js | Reuse by exporting from campaign.js (2 line change, additive) |

## Summary

Every file + function + endpoint + UI piece in Phase 11.3 has an existing analog in the codebase. The phase is mostly **pattern replication** with the Voyager endpoint swap being the one novel surface. This keeps risk low and review fast.
