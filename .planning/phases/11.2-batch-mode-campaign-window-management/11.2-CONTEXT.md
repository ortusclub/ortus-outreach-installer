# Phase 11.2: Batch-Mode Campaign + Window Management (INSERTED) — Context

**Gathered:** 2026-04-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Rework the campaign loop from per-lead round-robin to **per-profile batches of 5 (hard cap)**, swap the Rate & Limits UI from a daily/delay model to a **batches-per-hour** model, add **lazy profile launch** so unused profiles don't load LinkedIn, and make the Electron/Chromium windows **non-intrusive on macOS** (hidden Chromium windows + Electron tray mode).

Four coordinated capabilities:

1. **Batch loop** — every mode (including `connect_only`) processes 5 leads per profile per batch, then rotates; session-break cadence is removed (batches replace it).
2. **Batches-per-hour rate limits** — Rate & Limits form and backend honor "N batches per hour per profile" instead of "daily limit" + "delay min/max".
3. **Lazy profile lifecycle** — profile Chromium opens only on first batch, parks on `about:blank` between batches, closes after a gap threshold and re-opens on next batch.
4. **Non-intrusive windows** — GoLogin Chromium windows are minimized to the dock via AppleScript on macOS (not headless — retains LinkedIn trust). Electron app launches as a **menubar/tray app** with no dock window; click tray icon to toggle the dashboard. Closing the dashboard hides to tray rather than quitting.

Out of scope: retry logic, mode routing (`connect_only` / `message_only` / …), LinkedIn action layer (`performOutreach` and descendants), GoLogin SDK launch internals beyond the existing `extra_params`, any change to throttle/parking logic from 11.1.

</domain>

<decisions>
## Implementation Decisions

### Batch cadence

- **D-01:** **5 leads per batch per profile** — hard cap, not configurable upward. Matches the existing `LEADS_PER_ROTATION = 5` used for messaging/OP/InMail modes at `src/campaign.js:611-614`. This phase extends it to ALL modes, including `connect_only`.
- **D-02:** Within a batch, **gap between leads** = existing `delayMin..delayMax` (default 15–45s), renamed in the UI to "Gap between leads within a batch" but keeping the same field semantics.
- **D-03:** Between batches for the same profile, the gap derives from `batches_per_hour`: `wait = (3600 / batches_per_hour) seconds − time_just_spent_on_this_batch`. Minimum floor of 60s between batches regardless.
- **D-04:** The per-15-leads session break at `src/campaign.js:916-918` (10–20 min pause) is **removed**. Batches + between-batch waits replace it. This is a deliberate simplification — the old session-break was the v1.0 way of achieving what explicit batches + rate-limits do more cleanly.
- **D-05:** Throttle from Phase 11.1 still applies inside batches. If RAM/CPU spikes mid-batch, the per-lead delay within the batch still multiplies per `computeDelayMultiplier` (the existing composition).

### Rate-limit UI

- **D-06:** In the Rate & Limits form at `public/index.html:154`, **replace "Daily limit"** with a single new field: **"Batches per hour"** (per profile). Reasonable range 1–6 (UI validates). Default 2 → 10 leads/hour/profile, aligned with safe LinkedIn cadence.
- **D-07:** Keep "delay min / max seconds" fields, **relabel as "Gap between leads within a batch"**. Default 15/45 unchanged.
- **D-08:** **Daily cap** becomes implicit: `batches_per_hour × 5 × active_hours`. No explicit daily-limit field. If an operator wants to cap harder, they set `batches_per_hour` lower. Existing `dailyLimit = 40` parameter in `startCampaign` signature is kept as a backend hard ceiling for safety (e.g., if someone sets batches_per_hour=6 for a 24h run = 720 leads/day, dailyLimit would still cap at 40).
- **D-09:** **Legacy config back-compat:** when a saved schedule / history entry loads with old `dailyLimit`/`delayMin`/`delayMax` fields, the Rate & Limits form populates with default `batches_per_hour=2` and the saved `delayMin`/`delayMax`. No automatic conversion of the old field. A one-time dashboard toast explains the change.

### Profile lifecycle

- **D-10:** **Lazy launch** — profile Chromium opens only when that profile's first batch is about to start, NOT upfront at campaign start (removes the current `STEP 1` warmup-all-profiles loop at `src/campaign.js:416-548`).
- **D-11:** **First-batch warmup** — the first time a profile opens in a campaign session, run the existing 20s home-page health check before processing its first lead. Skipped on subsequent re-opens within the same session.
- **D-12:** **Between batches**, keep the browser alive and **park on `about:blank`** (honors Phase 11.1's `cfg.PARK_PAGE`). No LinkedIn rendering during the gap.
- **D-13:** **Gap threshold for close** — if the computed between-batch wait is **> 15 minutes**, close the browser entirely rather than parking. Re-open next batch (triggers first-batch-warmup again). Threshold is env-configurable: `PROFILE_CLOSE_GAP_MIN` (default 15).
- **D-14:** Profile-health errors (login page detected, weekly limit, etc.) still close the profile immediately, same as today. No change to error paths.

### Chromium window hiding (macOS)

- **D-15:** **Keep the existing `--window-position=-2400,-2400`** flag on `src/gologin-launcher.js:63` AND `src/local-launcher.js:58`. It doesn't fully hide on macOS but costs nothing and still helps on Linux/Windows.
- **D-16:** **On macOS only, add an AppleScript post-launch step** that sends each Chromium window to minimized state (shows in dock but not on desktop). Fires once per profile launch, after GoLogin returns the process handle, targeting the specific PID/window. Failures are swallowed (best-effort — do not break the campaign).
- **D-17:** **No headless mode.** LinkedIn fingerprints headless Chromium and can flag accounts. Keeping a real rendered window that is minimized is the right trade-off.
- **D-18:** **Operator escape hatch** — a "Show browsers" button in the dashboard that un-minimizes all currently-open Chromium windows via AppleScript. Used for debugging. Not required for normal operation.

### Electron tray mode

- **D-19:** **Launch mode:** tray icon + NO dock window on start. `app.dock.hide()` on macOS; tray icon appears in the menu bar with the Ortus logo.
- **D-20:** **Tray menu** exposes: "Show Dashboard" / "Start Campaign" (shortcut — opens dashboard and focuses the campaign form) / "Show Browsers" / "Quit". Clicking the tray icon toggles the dashboard window.
- **D-21:** **Dashboard close (X) behavior:** hides the window to tray instead of quitting. Quit is only via tray menu or Cmd+Q. Prevents accidental campaign interruption.
- **D-22:** **On Windows/Linux**, same pattern (`Tray` API works cross-platform); adapt as needed (no `app.dock.hide()` equivalent needed outside macOS).

### Claude's Discretion

- Exact AppleScript invocation style for minimize (`osascript -e '...'` vs `applescript` npm module vs `execFile` with a script file). Prefer the lowest-dependency option.
- How to structure the new batch-loop code inside `src/campaign.js` — inline refactor vs. extracted helper. Plan should preserve the existing round-robin structure for diff clarity if possible.
- Whether `batches_per_hour` lives in `startCampaign`'s parameter signature or comes in via a config object. Whatever matches the existing signature style.
- Dashboard toast implementation for D-09 legacy back-compat — reuse any existing toast pattern, or simple inline banner.
- Tray icon asset — reuse the existing Ortus logo PNG if one exists in `build/`; generate a 22×22 mono version if needed for macOS menubar.
- Default tray-app behavior on second-launch-while-already-running (focus existing tray vs. no-op).

<specifics>
## Specific Ideas

- **Boss directive:** "batches of five, never more" — 5 is a hard ceiling, not a starting point.
- **Operator observation:** "when the page goes to a blank one, CPU drops from 79% to 59%, RAM from 98% to 79%" — parking already works; the batch model preserves and extends this by ensuring profiles are parked for much longer stretches.
- **Non-intrusive:** "hidden but can open easily, not in the face of people when they open up" — minimized-to-dock is the target pattern, not off-screen-forever.
- **Mental model:** the app should behave like a background sync service (mail clients, Dropbox) — menubar-first, window on demand.

</specifics>
