# Phase 11.1: Resource-Aware Campaign Execution (INSERTED) - Context

**Gathered:** 2026-04-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the campaign loop visibly aware of the host machine's resource state. Three coordinated capabilities:

1. **Live RAM/CPU readout** in the dashboard, updated on the existing 2-second status poll.
2. **Idle profile parking** — between every lead, each profile navigates to a low-RAM page and back, slashing the per-profile RAM footprint during the delay window.
3. **Dynamic throttle** — when system resources cross a threshold, the per-lead delay multiplier increases automatically; when resources recover, normal pacing resumes.

Out of scope: GPU monitoring, retuning the Chromium memory flags / `protocolTimeout` / retry backoff (already done in quick task `260421-ot5`), changing the campaign orchestrator's mode logic or the LinkedIn action layer.

</domain>

<decisions>
## Implementation Decisions

### Resource counter UI

- **D-01:** Readout lives as new tiles in the existing `.header-stats` strip in the page header (`public/index.html:69`). No new layout pattern — extends the existing Today / 7D / Errors / Passover row.
- **D-02:** Three new tiles: **RAM** (percent), **CPU** (percent), **Browsers** (count + combined RAM, e.g. `5·1.4GB`).
- **D-03:** Format is number + color state. Ink → amber → red as values climb across thresholds. No sparkline, no breakdowns. Color thresholds match the throttle thresholds (D-04) so the visual signal and the behavioral signal are the same number.
- **D-04:** Sampling cadence reuses the existing 2-second `pollStatus()` loop (`public/js/app.js:1429` → `/api/campaign/status` at `src/server.js:429` → status payload from `campaign.js:951`). No new timer.

### Throttle policy

- **D-05:** Throttle **engages** when **RAM > 80%** OR **load1 > cpus * 0.9**. RAM is the primary signal (the user's stated pain point); CPU acts as a backstop for runaway-process cases.
- **D-06:** Throttle **releases** when **RAM < 70%** AND **load1 < cpus * 0.7** (both must be true). Hysteresis built in to prevent flapping at the boundary.
- **D-07:** "Throttled" multiplies the per-lead delay range by **2x** (e.g. `delayMin=30, delayMax=60` → `60–120s` while throttled). Returns to 1x on release.
- **D-08:** Throttle multiplier **stacks** with the existing single-profile 2x multiplier at `src/campaign.js:851`. Worst case = single-profile + throttled = **4x**. Aligns with the "when in doubt, slow down" stance from PROJECT.md.
- **D-09:** Session-break cadence (every 15 leads, 10–20 min pause at `campaign.js:853`) is **not** modified by the throttle. Throttle only touches the per-lead delay window.

### Idle parking

- **D-10:** Idle page is **`about:blank`**. Cheapest possible page (~20–40 MB vs ~200–400 MB for a loaded LinkedIn page). Profile cookies / session unaffected — only the rendered page changes.
- **D-11:** Parking happens **always between every lead**, not only when throttled. Each profile's loop becomes: navigate to lead → perform action → navigate to about:blank → wait `delayMin..delayMax` → navigate to next lead. Profiles never sit on a loaded LinkedIn page during the delay window.
- **D-12:** Re-arrival on LinkedIn after parking is a normal `page.goto(leadUrl)` — no special restoration logic. LinkedIn's session cookie does the work; cached assets reduce the practical cost of the re-load.

### Operator controls & visibility

- **D-13:** When the throttle is engaged, the dashboard surfaces it two ways simultaneously:
  - A **banner** in the Live Status section: `⚠ SLOW MODE — RAM 88%, delays 2x`
  - The **RAM tile** in the header turns red (and CPU tile if CPU was the trigger)
  Banner disappears and tile colors return to normal when throttle releases.
- **D-14:** Thresholds and multiplier are **hardcoded defaults with optional `.env` overrides**. Knobs:
  - `RAM_THROTTLE_PCT` (default 80)
  - `RAM_RELEASE_PCT` (default 70)
  - `CPU_THROTTLE_LOAD_FACTOR` (default 0.9)
  - `CPU_RELEASE_LOAD_FACTOR` (default 0.7)
  - `THROTTLE_MULTIPLIER` (default 2)
  - `PARK_PAGE` (default `about:blank`)
  - `IDLE_PARKING_ENABLED` (default true) — kill switch in case parking causes any LinkedIn weirdness in the field
  No settings UI in the dashboard for these.

### Claude's Discretion

- Sampling library choice for per-Chromium RAM (D-02 needs per-PID stats). Likely candidates: `pidusage` (small, focused) or walking `os` + `child_process` natively. Decide during planning based on cross-platform behavior (macOS / Windows are both in scope — colleagues use both).
- Exact CSS color tokens for the amber / red states (use existing `var(--red)` and pick an amber token from the palette).
- Where in `campaign.js` the throttle check fires (per-iteration of the round-robin loop is the obvious spot, but planner can refine).
- Whether the per-Chromium RAM aggregation runs on every 2s tick or on a slower cadence (e.g. 5s) since it's heavier than `os.freemem()`.
- How to wire the parking step without touching `performOutreach` (per PROJECT.md non-negotiable). Likely: insert before/after the existing `delay` call in the round-robin loop.

### Folded Todos

None — no pending todos matched this phase.

Phase 11.1 should refactor this to return the raw numeric snapshot (`{ ramPct, load1, cpuCount, freeMem, totalMem }`) so both the throttle decision and the dashboard tile can consume the same source. The current "warnings" use can stay as a downstream presentation concern.
- **Status poll at `/api/campaign/status` (`src/server.js:429`)** — Single API endpoint already polled every 2s by the dashboard. Add the resource snapshot to its response payload (built in `campaign.js:951-963`) — no new endpoint needed.
- **Frontend poll loop at `public/js/app.js:1429-1442`** — Single place to render the new tiles + banner state from the status payload.
- **Existing `delayMultiplier` at `src/campaign.js:851`** — Today: static, decided once at campaign start (`2.0` for single-profile only). Phase 11.1 makes this dynamic: re-evaluated each iteration as `singleProfileMult * throttleMult`.
- **`.header-stats` strip in `public/index.html:69`** with CSS at `public/css/style.css:516-554` — Tile styling already supports `.v.err` (red). Add `.v.warn` (amber) for the throttle-pending state if not already present.

### Established Patterns
- **Wrap-don't-touch core logic** — All v2.0 hardening (auth, scheduling, history, dedup) added new modules / new wrappers around existing functions. Phase 11.1 follows the same: a new `src/resource-monitor.js` module + minimal touches to `campaign.js`.
- **`.env`-driven config with code defaults** — Existing pattern (e.g. ElevenLabs/Twilio creds, batch concurrency cap). Throttle knobs plug in the same way.
- **Status-poll-driven UI** — All live-status data flows through the 2s `/api/campaign/status` poll. No WebSockets, no SSE. Phase 11.1 stays on this rail.
- **Vanilla JS dashboard** — No framework. New tiles are imperative DOM updates in `app.js`.

### Integration Points
- `src/campaign.js` — Add `parkProfile(page)` call between performOutreach and the delay sleep in the round-robin loop. Add throttle re-evaluation at the start of each iteration. Add resource snapshot to the status payload.

- `public/index.html` — Three new `<div class="header-stat">` tiles in `#header-stats`.

Keeps the throttle state machine testable in isolation.

<specifics>
## Specific Ideas

- "It would also be easier for testing to check if something is getting better or not" — the resource counter is partly a diagnostic tool, not just a runtime safety net. Defaults and color thresholds should be tuned so an operator running a campaign can *see* the trend, not just a binary OK/throttled signal.
- "GoLogin accounts that are not being used or called at the moment go to a web page with very low RAM consumption. For example, just a text-based page or Google or whatever." — `about:blank` chosen as the cheapest interpretation of "very low RAM consumption."
- Colleagues run on slow, overloaded machines (per `project_gologin_user_hardware` memory) — every default in this phase should assume the user is RAM-starved, not abundant.

</specifics>

<deferred>
## Deferred Ideas

- **GPU monitoring** — Discussed and explicitly skipped. RAM and CPU are the binding constraints; GPU on LinkedIn pages is mostly idle and wouldn't change the throttle decision. Reconsider only if a future case shows RAM and CPU both fine but the machine still feels stuck.
- **Tiered throttling (2x at 80%, 3x at 90%)** — Considered but rejected as added state for marginal benefit. If 2x isn't enough cooling at 80%, the right move is to lower the threshold, not add a tier.
- **Pause-on-throttle (hard stop instead of slow-mode)** — Rejected as too disruptive to operator workflow.
- **Settings UI in the dashboard for thresholds** — Rejected for now; `.env` overrides cover the testing-iteration use case without exposing knobs colleagues shouldn't touch.
- **Per-campaign override of parking behavior** — Possible knob (e.g. "this campaign keeps profiles on LinkedIn") but no concrete need surfaced. `IDLE_PARKING_ENABLED` env var is the kill switch instead.
- **Force-throttle button** for testing UI behavior — useful but Claude-discretion / could be added during implementation if needed.

</deferred>
