## Throttle policy

### Q1 — Trigger signal and threshold

| Option | Description | Selected |
|--------|-------------|----------|
| RAM-primary, CPU as backstop | Trigger on RAM > 80% OR load1 > cpus*0.9. Release at RAM<70% AND load1<cpus*0.7. | ✓ |
| RAM only | Simpler — only RAM% triggers. | |
| Both RAM and CPU must trip | Conservative — only throttle when both signals say 'bad'. | |

**User's choice:** RAM-primary with CPU backstop. Hysteresis baked in to prevent flapping at the boundary.

### Q2 — When the throttle engages, what behavior changes?

| Option | Description | Selected |
|--------|-------------|----------|
| Multiply per-lead delay 2x | 30-60s delay becomes 60-120s while throttled. | ✓ |
| Multiply 2x AND raise session-break frequency | Both: 2x delay + breaks every 8 leads instead of 15. | |
| Tiered — 2x at 80%, 3x at 90% | Multi-stage backoff. | |
| Pause campaign entirely until released | Hard stop. | |

**User's choice:** 2x multiplier on delays only. Session-break cadence stays untouched.

### Q3 — Stack with existing single-profile 2x?

| Option | Description | Selected |
|--------|-------------|----------|
| Stack (4x total) | Single-profile (2x) × throttled (2x) = 4x worst case. | ✓ |
| Don't stack — max(throttle, single-profile) | Cap at 2x regardless. | |
| Throttle replaces single-profile multiplier | When throttled, ignore the single-profile rule. | |

**User's choice:** Stack to 4x. Most defensive — single profile on a stressed machine gets the gentlest treatment.

## Idle parking

### Q1 — What page should an idle profile sit on?

| Option | Description | Selected |
|--------|-------------|----------|
| about:blank | ~20-40 MB. Cheapest possible page. | ✓ |
| google.com | ~80-120 MB. User-suggested option. | |
| Local minimal HTML page | Same cost as about:blank but easier to identify in screenshots. | |

**User's choice:** about:blank. Lowest possible RAM, no network, no JS, no compositor work.

### Q2 — When should a profile be parked?

| Option | Description | Selected |
|--------|-------------|----------|
| Always between leads | Park immediately after each lead's actions complete. | ✓ |
| Only when throttled | Park only while resource throttle is engaged. | |
| Park profiles not in current round | Per-profile state machine — only active profile keeps LinkedIn loaded. | |
| Don't park automatically | Counter + throttle only, no parking. | |

**User's choice:** Always between leads. Maximum RAM relief, simplest mental model.

## Operator controls & visibility

### Q1 — How visible should the 'we're throttling' state be?

| Option | Description | Selected |
|--------|-------------|----------|
| Banner + tile color shift | Banner explains why ('SLOW MODE — RAM 88%, delays 2x'), RAM tile turns red. | ✓ |
| Tile color only | Quieter UI but operators may not connect cause to effect. | |
| Banner only, no color | Loses at-a-glance signal. | |
| Just write it to logs | Easy to miss. | |

**User's choice:** Banner + tile color. Operators immediately see why their campaign got slower.

### Q2 — Configurable or hardcoded?

| Option | Description | Selected |
|--------|-------------|----------|
| Hardcoded defaults + .env overrides | Defaults baked in; power-users override via .env. No dashboard knobs. | ✓ |
| Settings UI in dashboard | Form inputs for the knobs. Best for fast iteration. | |
| Hardcoded only | No overrides at all. | |

**User's choice:** Hardcoded + .env overrides. Covers the testing-iteration use case without exposing knobs colleagues shouldn't touch.
