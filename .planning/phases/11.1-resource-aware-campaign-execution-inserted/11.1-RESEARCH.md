# Phase 11.1: Resource-Aware Campaign Execution (INSERTED) - Research

**Researched:** 2026-04-22
**Domain:** Node.js process / OS resource sampling, Puppeteer session hygiene, vanilla-JS dashboard tile rendering
**Confidence:** HIGH (core APIs), MEDIUM (per-PID aggregation cost), MEDIUM (about:blank heap release)

## Summary

Phase 11.1 wraps the existing `performOutreach`/round-robin loop with a three-part resource story: a lightweight `resource-monitor.js` module that samples OS RAM + load and per-Chromium RSS, a `parkProfile(page)` wrapper that lands each profile on `about:blank` during the delay window, and a dynamic `delayMultiplier` that re-evaluates each iteration against the sampled state. The existing `checkHostHealth()` (`campaign.js:56-72`) already proves the approach — this phase extends it from a one-shot preflight into a live loop.

The single significant unknown — and the first thing the planner must address — is **how to obtain Chromium PIDs for per-browser RSS aggregation**. The codebase connects to GoLogin-spawned Chromium via `puppeteer.connect({ browserWSEndpoint })` (`gologin-launcher.js:84-88`), and per official Puppeteer docs, `browser.process()` returns `null` in that mode. The GoLogin SDK internally holds the child process handle as `this.processSpawned` (`node_modules/gologin/src/gologin.js:1017-1018`), so the PID exists — it just isn't on the public surface of our launcher. Two viable paths exist (see §Standard Stack and §Don't Hand-Roll).

**Primary recommendation:** Add `src/resource-monitor.js` exporting two pure functions — `sample(browsers)` that returns `{ ramPct, load1, cpuCount, browsers: [{pid, rssMb}], totalBrowserRssMb }` using `pidusage` for per-PID RSS, and `decideThrottle(currentState, sample, config)` that implements the hysteresis state machine. Expose the GoLogin `processSpawned.pid` from `gologin-launcher.js` so the campaign loop can pass an array of Chromium PIDs into `sample()`. Add `parkProfile(page)` that calls `page.goto('about:blank', { waitUntil: 'domcontentloaded', timeout: 5000 })` with a swallow-and-log catch, invoked between `performOutreach` and the sleep in the round-robin loop. Compose the new throttle multiplier with the existing single-profile multiplier at `campaign.js:851` multiplicatively.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Resource counter UI**
- **D-01:** Readout lives as new tiles in the existing `.header-stats` strip in the page header (`public/index.html:69`). No new layout pattern — extends the existing Today / 7D / Errors / Passover row.
- **D-02:** Three new tiles: **RAM** (percent), **CPU** (percent), **Browsers** (count + combined RAM, e.g. `5·1.4GB`).
- **D-03:** Format is number + color state. Ink → amber → red as values climb across thresholds. No sparkline, no breakdowns. Color thresholds match the throttle thresholds (D-04) so the visual signal and the behavioral signal are the same number.
- **D-04:** Sampling cadence reuses the existing 2-second `pollStatus()` loop. No new timer.

**Throttle policy**
- **D-05:** Throttle engages when **RAM > 80%** OR **load1 > cpus * 0.9**. RAM is the primary signal; CPU is backstop for runaway-process cases.
- **D-06:** Throttle releases when **RAM < 70%** AND **load1 < cpus * 0.7** (both must be true). Hysteresis prevents flapping.
- **D-07:** "Throttled" multiplies per-lead delay range by **2x** (e.g. `30–60s` → `60–120s`). Returns to 1x on release.
- **D-08:** Throttle multiplier **stacks** with the single-profile 2x at `src/campaign.js:851`. Worst case = single-profile + throttled = **4x**.
- **D-09:** Session-break cadence (every 15 leads, 10–20 min pause at `campaign.js:853`) is **not** modified by the throttle.

**Idle parking**
- **D-10:** Idle page is **`about:blank`**.
- **D-11:** Parking happens **always between every lead**, not only when throttled. Loop: navigate to lead → perform action → navigate to about:blank → wait delayMin..delayMax → navigate to next lead.
- **D-12:** Re-arrival on LinkedIn is a normal `page.goto(leadUrl)` — no special restoration logic.

**Operator controls & visibility**
- **D-13:** Throttle engaged surfaces two ways: a **banner** in the Live Status section (`⚠ SLOW MODE — RAM 88%, delays 2x`), and the **RAM tile** (or CPU tile, whichever tripped) turns red.
- **D-14:** Thresholds and multiplier are hardcoded defaults with optional `.env` overrides:
  - `RAM_THROTTLE_PCT` (default 80), `RAM_RELEASE_PCT` (default 70)
  - `CPU_THROTTLE_LOAD_FACTOR` (default 0.9), `CPU_RELEASE_LOAD_FACTOR` (default 0.7)
  - `THROTTLE_MULTIPLIER` (default 2)
  - `PARK_PAGE` (default `about:blank`)
  - `IDLE_PARKING_ENABLED` (default true) — kill switch
  No settings UI.

Data flow (primary use case — one loop iteration during a running campaign):
1. Operator starts campaign → N profiles spawned → each PID recorded via `getProfilePid`.
2. Every iteration: `sample(pids)` pulls RAM/CPU/per-browser RSS → `decideThrottle(...)` updates the state machine → loop applies delay multiplier.
3. Every 2s, dashboard polls `/api/campaign/status` → reads `campaign._lastSample` and `campaign._throttle` → renders tiles + banner.
4. Between `performOutreach` and sleep: `parkProfile(page)` lands the profile on `about:blank`; after sleep, the next iteration's `page.goto(leadUrl)` brings it back.

### Pattern 1: Pure `decideThrottle` function (hysteresis state machine)

**What:** Single pure function that takes the previous throttle state, the current sample, and config; returns the new state. No timers, no I/O, no side effects. Unit-testable in isolation.

**When to use:** Any time the loop iterates (per-iteration re-evaluation, as D-08 and §Claude's Discretion allow).

**Example:**

```javascript
// Source: Pure function pattern, verified against D-05/D-06/D-07 in CONTEXT.md
// Signature: (currentState, sample, config) → newState

export function decideThrottle(state, sample, cfg) {
  const { ramPct, load1, cpuCount } = sample;
  const upperRam  = cfg.RAM_THROTTLE_PCT;           // 80
  const lowerRam  = cfg.RAM_RELEASE_PCT;            // 70
  const upperLoad = cpuCount * cfg.CPU_THROTTLE_LOAD_FACTOR; // cpus * 0.9
  const lowerLoad = cpuCount * cfg.CPU_RELEASE_LOAD_FACTOR;  // cpus * 0.7

  const ramHigh  = ramPct > upperRam;
  const loadHigh = load1  > upperLoad;
  const ramLow   = ramPct < lowerRam;
  const loadLow  = load1  < lowerLoad;

  let active = state.active;
  if (!state.active && (ramHigh || loadHigh)) {
    active = true;  // engage (D-05: OR)
  } else if (state.active && ramLow && loadLow) {
    active = false; // release (D-06: AND)
  }
  // otherwise: stay the same (between thresholds → no transition)

  const reasons = [];
  if (active && ramPct  > lowerRam)  reasons.push(`RAM ${ramPct.toFixed(0)}%`);
  if (active && load1   > lowerLoad) reasons.push(`load1 ${load1.toFixed(1)}`);

  return {
    active,
    reason: reasons.join(' + '),
    multiplier: active ? cfg.THROTTLE_MULTIPLIER : 1,
  };
}
```

### Pattern 2: Cached sample + lazy refresh on poll vs. per-iteration refresh

The existing status endpoint is read-only (`getCampaignStatus` at `campaign.js:951`). The campaign loop writes `campaign._lastSample` on every iteration, and the status endpoint reads that cached value. This keeps sampling on the one rail that matters (the loop), not the two rails (loop AND status HTTP) which would double the per-2s sampling cost.

- Iteration cadence is governed by the existing `delayMin..delayMax` sleep (15–45s by default, 30–60s for single-profile). That's the natural per-sample cadence for throttle decisions.
- Dashboard 2s poll simply reads the cached `_lastSample` — fresh enough for the UI (the sample is at most one lead-delay old, and the RAM trend changes slowly enough that stale-by-15-seconds is fine for a visual signal).
- If the cache is `null` (no campaign running), the status endpoint returns `resources: null` — dashboard shows `—` in the tiles, same as existing behavior for `currentProfile` when idle.

### Pattern 3: Multiplicative composition of existing `delayMultiplier`

**Current (at `campaign.js:851`):**

```javascript
const delayMultiplier = (!isMessageMode && profileIds.length === 1) ? 2.0 : 1.0;
// ...

```

**Target (D-08):**

```javascript
const singleProfileMult = (!isMessageMode && profileIds.length === 1) ? 2.0 : 1.0;
const throttleMult      = campaign._throttle?.multiplier ?? 1;
const delayMultiplier   = singleProfileMult * throttleMult;  // 1, 2, or 4
// ...
waitMs = Math.floor(waitMs * delayMultiplier);
if (delayMultiplier > 1) {
  const parts = [];
  if (singleProfileMult > 1) parts.push(`single-account ${singleProfileMult}x`);
  if (throttleMult > 1) parts.push(`throttled ${throttleMult}x`);

}
```

This preserves the existing single-profile path byte-identically when not throttled (`1.0 * 1 === 1.0` is a no-op vs. the current `1.0`).

### Anti-Patterns to Avoid

- **Sampling inside `performOutreach`**: forbidden by PROJECT.md (core logic untouched) and would tie sample cadence to whatever performOutreach's internal timing is. Sample at the loop boundary only.
- **Separate `setInterval` timer for sampling**: adds a new async rail that the existing abort mechanism (`campaign._abort`) doesn't know about. Use the loop-driven pattern instead.
- **Blocking the loop on sample errors**: `pidusage` can fail if a PID has already exited (race between close and sample). Wrap in try/catch and fall back to `{ browsers: [], totalBrowserRssMb: 0 }` for the sample.
- **Setting `_throttle` from the HTTP handler**: one-way flow — loop writes, handler reads. Prevents races.
- **Modifying the session-break path** (`campaign.js:853-859`): D-09 forbids it. Touch only the `else` branch around line 864-869.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Per-PID RSS on mac + Windows | `child_process.execFile('ps', ...)` + CSV/text parsing, branching on `process.platform` | `pidusage` (4.0.1, 36 KB, 1 dep) | pidusage handles: PID-not-found, negative delta math for CPU %, Windows WMIC vs. fallback, array batching. Reimplementing = ~150 lines per platform × 2 platforms + edge cases. [VERIFIED: github.com/soyuka/pidusage CI matrix] |
| Chromium PID discovery via shell walking | `pgrep -P <parentPid>` on mac + `wmic process where (ParentProcessId=N)` on Windows | `GL.processSpawned.pid` exposed by gologin-launcher + pass directly into pidusage | GoLogin already holds the PID; exposing it is a 3-line change (new `getProfilePid` export). Walking processes is fragile — renderer PIDs change constantly. [VERIFIED: `gologin/src/gologin.js:1017-1018`] |
| CPU % on Windows (loadavg returns `[0,0,0]`) | Wiring `loadavg-windows` or `windows-cpu` npm package | 20-line `os.cpus()` delta sampling in `resource-monitor.js` | Minimal code, no new deps. Both npm alternatives add maintenance burden for a trivial calculation. See §Code Examples: CPU fallback. [CITED: https://github.com/fider/loadavg-windows] |
| Hysteresis state machine | Ad-hoc `if (throttled && !below) ...` in the loop | Pure `decideThrottle(state, sample, cfg)` function in `resource-monitor.js` | Testable in isolation (no I/O, no os module mocking). See §Validation Architecture. |
| Profiling Chromium heap | CDP Performance / HeapProfiler domains | Per-process RSS via pidusage | Heap profiling is diagnostic; RSS is what the throttle decision actually cares about. CDP heap APIs add I/O cost we don't need. |

**Key insight:** The most expensive hand-rolled work here would be cross-platform process introspection. pidusage solves that in a single 36 KB dep. Everything else (the state machine, the delay composition, the status payload shape, the tile render) is small pure code we should write.

## Common Pitfalls

### Pitfall 1: `browser.process()` returns null with `puppeteer.connect()`

**What goes wrong:** Code like `browser.process().pid` throws `TypeError: Cannot read property 'pid' of null` inside the campaign loop.

**Why it happens:** The GoLogin launcher connects via WebSocket (`gologin-launcher.js:84-88`). Per official Puppeteer docs, `browser.process()` returns `ChildProcess | null` and is null when connected via `puppeteer.connect()`. The Chromium child process handle lives inside the GoLogin SDK as `GL.processSpawned`, not on the Puppeteer `Browser` object.

**How to avoid:** Expose the PID from gologin-launcher:

```javascript
// src/gologin-launcher.js — add this new export
export function getProfilePid(profileId) {
  const GL = activeProfiles.get(profileId);
  return GL?.processSpawned?.pid ?? null;
}
```

Then in `campaign.js`, collect PIDs from `activeSessions` at sample time:

```javascript
import { getProfilePid } from './gologin-launcher.js';

const activePids = activeSessions
  .filter(s => s.profileId !== 'local-browser')
  .map(s => getProfilePid(s.profileId))
  .filter(Boolean);
```

**Warning signs:** `browsers: []` always, even with 3 GoLogin profiles running. Indicates the PID-extraction path returned null across the board — add a one-time diagnostic log on first sample if `browserPids.length === 0` but `activeSessions.length > 0`.

[CITED: https://pptr.dev/api/puppeteer.browser.process verified 2026-04-22]

### Pitfall 2: `pidusage` throws when a PID has exited between samples

**What goes wrong:** During profile teardown or a Chromium crash, `pidusage([pid])` rejects with `Error: No matching pid found`, bubbling up through the loop and killing the campaign.

**Why it happens:** pidusage walks procfile / wmic at sample time; if the PID vanished in the last few ms, the lookup fails.

**How to avoid:** Wrap the call and degrade gracefully:

```javascript
let pidStats = {};
try {
  pidStats = await pidusage(browserPids);
} catch (err) {
  // Profile may have closed mid-sample — fall back to empty.
  // Caller already has RAM/load from os.freemem/loadavg.
}
const browsers = browserPids
  .map(pid => ({ pid, rssMb: Math.round((pidStats[pid]?.memory ?? 0) / 1024 / 1024) }))
  .filter(b => b.rssMb > 0);
```

**Warning signs:** Status payload shows non-zero RAM/CPU but `browsers: []`. Log a one-line warning at most once per minute so the log doesn't flood.

### Pitfall 3: `os.loadavg()` returns `[0, 0, 0]` on Windows

**What goes wrong:** The throttle never engages on Windows — RAM-only engagement works but CPU backstop (D-05) silently does nothing. Worse, the CPU tile shows "0" which looks broken.

**Why it happens:** Load average is a Unix concept; Node on Windows always returns `[0, 0, 0]`. This is documented and unfixable at the `os` module level.

**How to avoid:** Compute a CPU % from `os.cpus()` delta across two samples, and use that as the Windows backstop:

```javascript
// Inside resource-monitor.js — module-level state for delta sampling
let _prevCpuTimes = null;

function getCpuPct() {
  const cpus = os.cpus();
  const now  = cpus.map(c => ({
    idle:  c.times.idle,
    total: Object.values(c.times).reduce((a, b) => a + b, 0),
  }));
  if (!_prevCpuTimes) { _prevCpuTimes = now; return 0; }
  let idleDiff = 0, totalDiff = 0;
  for (let i = 0; i < now.length; i++) {
    idleDiff  += now[i].idle  - _prevCpuTimes[i].idle;
    totalDiff += now[i].total - _prevCpuTimes[i].total;
  }
  _prevCpuTimes = now;
  return totalDiff > 0 ? (1 - idleDiff / totalDiff) * 100 : 0;
}

// On Windows: use cpuPct (0-100). Convert threshold: cpuPct > 90 ≈ load1 > cpuCount * 0.9.
// On macOS: use os.loadavg()[0] directly (matches existing checkHostHealth()).
const isWindows = process.platform === 'win32';
const load1 = isWindows ? (getCpuPct() / 100) * os.cpus().length : os.loadavg()[0];
```

Treating Windows CPU % as "equivalent load" (`cpuPct/100 * cpuCount`) lets the same threshold expression (`load1 > cpuCount * 0.9`) work on both OSes with no branching in `decideThrottle`.

**Warning signs:** On a Windows machine under heavy CPU, the CPU tile stays at "0" and throttle never engages on CPU alone. Test explicitly by running the Windows build under `yes > /dev/null` equivalent (or a real CPU burner) and verifying load1 / cpuPct rises.

[CITED: https://github.com/fider/loadavg-windows (documents the [0,0,0] behavior explicitly)]

### Pitfall 4: `about:blank` doesn't fully release the renderer process

**What goes wrong:** Per the Puppeteer community and several long-standing issues, `page.goto('about:blank')` reduces DOM / JS-heap / GPU-texture pressure but **does not terminate the renderer process**. RSS drops (often 50-70%) but not to zero.

**Why it happens:** Chromium keeps the renderer warm for fast re-navigation. The renderer process is associated with the `Page` / tab, not the loaded URL.

**How to avoid:** Set expectations — `about:blank` is the right tool for THIS phase (D-10 locks it) because:
1. It's what the user asked for ("just a text-based page or Google or whatever").
2. It preserves cookies (D-12 requires session intact).
3. It's fast (local navigation, no network).

If the RAM savings from `about:blank` prove insufficient in field testing, the escalation path is `page.close()` + `browser.newPage()` per lead — heavier but guaranteed cleanup. Out of scope for this phase.

**Warning signs:** With 5 profiles parked on `about:blank`, total browser RSS does not drop meaningfully from 5 active LinkedIn tabs. If that's observed, document as a follow-up; don't re-architect in 11.1.

[CITED: Puppeteer issue #9283 "Chrome browser requests leak memory" + about:blank recommendation pattern from devforth.io blog, verified 2026-04-22]

### Pitfall 5: Per-iteration sampling thrashes on very short delays

**What goes wrong:** In message mode (`delayMin..delayMax` configurable and user-set), delays can drop to 5-10s. Sampling 3-5 browsers every 5s × several profiles = tens of sample calls per minute, each walking procfile / WMIC.

**Why it happens:** The "natural" cadence (per iteration) isn't fixed — it's driven by campaign settings.

**How to avoid:** Add a minimum sample interval in `resource-monitor.js`:

```javascript
let _cachedSample = null;
const MIN_SAMPLE_INTERVAL_MS = 5000;

export async function sample(browserPids) {
  if (_cachedSample && Date.now() - _cachedSample.sampledAt < MIN_SAMPLE_INTERVAL_MS) {
    return _cachedSample;
  }
  // ...actually sample...
  _cachedSample = { /* new sample */ };
  return _cachedSample;
}
```

5s is reasonable: it matches the retry-backoff granularity already in use (`attempt * 15000`) and keeps pidusage cost bounded regardless of campaign settings. Documented in §Claude's Discretion as a legitimate choice.

**Warning signs:** CPU overhead of Node server visibly rising in profiling, or user complaints about "dashboard feels slow." The 5s cap prevents this.

### Pitfall 6: Touching session-break branch violates D-09

**What goes wrong:** Applying the throttle multiplier to `waitMs` inside the session-break branch (`campaign.js:855-859`) stretches a 10-20 min pause to 20-40 min when throttled. Breaks the spec.

**Why it happens:** The naive refactor multiplies everything by `delayMultiplier`.

**How to avoid:** Only apply throttle in the `else` branch (lines 864-869). Leave the session-break and message-mode branches byte-identical. The diff should show three distinct logic paths:

```javascript
if (!isMessageMode && totalDone > 0 && totalDone % SESSION_BREAK_EVERY === 0) {
  // UNCHANGED — no throttle here
} else if (isMessageMode) {
  // UNCHANGED — no throttle here (message mode is its own cadence)
} else {
  // ONLY this branch gets throttleMult applied
}
```

**Warning signs:** Session-break log shows "40 min" or more. If observed, revert to not applying throttleMult in the other branches.

## Open Questions

1. **Should per-PID sampling run on every loop iteration or throttled to 5s?**
   - What we know: Loop cadence is 15–45s by default (30–60s single-profile). pidusage is cheap but non-trivial.
   - What's unclear: Whether operators will ever see a campaign with delays <5s.
   - Recommendation: Cap at 5s with `MIN_SAMPLE_INTERVAL_MS` (see §Pitfall 5). Safe default, no downside for slow campaigns, protects fast ones.

2. **Does pidusage need `safe-buffer` in Electron packaging?**
   - What we know: safe-buffer is a well-established pure-JS dep; Electron's main process is Node.js.
   - What's unclear: Whether the existing `asar: false` + electron-builder glob picks it up without extra config.
   - Recommendation: Ship and test. If the production DMG fails to find the module, add `pidusage` to electron-builder's unpack list.

3. **Should the throttle state persist across campaign stops?**
   - What we know: The current `campaign` state object is reset at `campaign.js:266-274` on every `startCampaign`.
   - What's unclear: Whether an operator would want "was throttled when I stopped → still shows banner" after stopping.
   - Recommendation: Follow existing pattern — clear `_throttle` and `_lastSample` on campaign start. If a stale banner annoys, stop sets `_throttle = null` too.
