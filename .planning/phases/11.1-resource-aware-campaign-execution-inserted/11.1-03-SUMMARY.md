# Plan 11.1-03 Summary — Sidebar UI + post-checkpoint hardening

## What was built

**Core deliverable (Tasks 1–3):**

- Three new header-strip tiles — **RAM**, **CPU**, **Browsers** — rendered after Passover in the existing `.header-stats` row. Visible without scrolling.
- `renderHeaderResources(resources)` and `renderThrottleBanner(throttle)` wired into the existing 2-second `pollStatus()`. No new timer, no new endpoint.
- RAM tile colors: ink when <70%, amber when 70–79%, red at ≥80%. CPU tile uses the same bands applied to `load1 / cpuCount * 100`.
- Browsers tile: `count·N.NGB` (dot separator, RSS in GB).
- Slow-mode banner in the Live Status section: `⚠ SLOW MODE — {reason}, delays {multiplier}x`. Hidden when `throttle.active` is false.
- `textContent` used for the `reason` field — XSS-safe for arbitrary throttle output. `aria-live="polite"` set on the banner.
- All new rendering sits inside the existing outer `try/catch` in `pollStatus()` — no regression risk to the 4 pre-existing tiles.

**Human-verify gap closure (post-checkpoint fixes):**

The first electron run surfaced two real UX issues the automated checks couldn't catch. Both were diagnosed against evidence (running process state, `vm_stat` vs `os.freemem()`) and fixed before approval:

1. **Tiles did not populate until the round-robin loop iterated.** Root cause: `campaign._lastSample` is only written inside `while (!campaign._abort)` at `src/campaign.js:556`, meaning tiles showed `—` for the entire ~60s warmup window (3 profiles × per-profile launch + health check + 20s idle hold). Fix: added `startAmbientSampling()` in `src/resource-monitor.js` — a 5-second server-wide sampler that runs from `app.listen`. `getCampaignStatus` falls back to the ambient sample when the loop hasn't written one. Round-robin samples still take precedence when present. Exposed `getActiveBrowserPids()` from `gologin-launcher.js` so the ambient sampler picks up browser RAM during warmup too.

2. **RAM% showed 98% when Activity Monitor showed 78%; CPU showed meaningless "5.6".** Root cause for RAM: `os.freemem()` on macOS only counts truly-free pages, excluding inactive and purgeable pages that the kernel reclaims on demand. This inflated the percentage by 20+ points. Fix: on darwin only, call `vm_stat`, sum `Pages free + Pages inactive + Pages purgeable`, compute `1 - available/total`. Falls back to `os.freemem()` on parse failure. Linux and Windows paths unchanged. Root cause for CPU: raw Unix load average is unintelligible to non-technical users. Fix: display as `(load1 / cpuCount) * 100` percent — puts CPU on the same scale as RAM and lines up with the 0.7/0.9 hysteresis thresholds semantically.

## Deviations from plan

1. **Added ambient sampler (not in original plan).** The plan assumed tiles would only need to work while the round-robin loop was running. Operator testing showed a ~60s warmup window with blank tiles. Added a server-wide 5s sampler as gap closure. Not breaking — campaign-loop samples still take precedence.

2. **Changed RAM calculation on macOS (not in original plan).** Plan used `os.freemem()` uniformly. Real-world testing on macOS showed 20+ point over-reporting. Added `vm_stat`-based calculation on darwin only; other platforms unchanged.

3. **Changed CPU display from raw load to percentage (not in original plan).** Plan specified `load1.toFixed(1)` as the display format. Operator feedback: "what does 5.6 mean?". Changed to `(load1 / cpuCount) * 100` as percent. Threshold logic unchanged (still relative to cpuCount).

4. **Banner placement.** Plan specified "between `campaign-warnings` and the Copy/Clear buttons." Implemented as specified.
