## Decisions Made

- **Seed throttle state inline vs. add a module-level helper.** Chose inline: `const prevThrottle = campaign._throttle || { active: false, reason: '', multiplier: 1 }`. Extracting a helper for one call site would be premature. If a second call site (e.g. Plan 03 dashboard mount) needs the default, we'll promote it then.
- **Park before or after the delay log.** Chose before: park → compute delay → sleep. Rationale: parking is an action on the profile (brief `goto`), the delay is the idle window itself; the user sees the park happen, then the wait log, then the wait. This matches the D-11 narrative ("between every lead, the profile navigates to PARK_PAGE before the delay sleep").
- **Enriched log naming.** Changed `single-account: 2x slower` to `single-account 2x` (no colon, no "slower") so the parts array joins cleanly as `single-account 2x + throttled 2x`. Backwards-compat concern: no tests or dashboard string-match on the old phrasing (grep confirmed).

## Threat Model Compliance

The plan's `<threat_model>` declared four threats. Compliance:

- **T-11.1-05 (parkProfile DoS during LinkedIn nav):** `parkProfile` is called strictly sequentially between `performOutreach` (which has finished) and the delay sleep. The next lead's `page.goto(leadUrl)` doesn't run until after the delay. No concurrent navigation. `IDLE_PARKING_ENABLED=false` is the env escape hatch (verified in unit test Plan 01).
- **T-11.1-06 (operator sets RAM_THROTTLE_PCT=1 to force throttle):** Accepted risk — if this happens every campaign runs at 4x delay. Self-correcting.
- **T-11.1-07 (hysteresis flap if RAM_THROTTLE_PCT == RAM_RELEASE_PCT):** Mitigated at Plan 01 via strict `>` / `<` comparisons in `decideThrottle`. This plan inherits that guarantee.
- **T-11.1-08 (silent throttle transitions):** Mitigated — the new transition log lines (`⚠ Throttle ENGAGED:` / `✓ Throttle RELEASED`) push into `campaign.logs` (capped at 500), visible via the dashboard log panel once Plan 03 ships.

No new threat surface introduced.
