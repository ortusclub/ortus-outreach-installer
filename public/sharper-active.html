Showing it's working

Three ways to render the three active phases — sending connections, introducing, checking status. Same data behind all three. Colour isn't a variable here: the app already means green = actively doing outreach, blue = monitoring/reading, gold = waiting on something. The alts differ in layout.

What the card shows today, all three phases

“Working…” — and an empty second line.
live-activity.mjs reads status.currentAction; _buildCloudActiveStatus never sets it, so l1 falls through to the literal string 'Working…' for 30–60s per lead. Introducing has no state of its own at all — it runs inside the acceptance sweep, so while the VM is writing intro messages to six people the card says “Checking for new acceptances…”.

Unmissable, and the chips solve a separate problem — right now nothing on the card tells you the fleet's state without opening the Accounts panel. Biggest layout change of the three, and the big name goes stale-looking on a 60s lead unless the seconds counter is ticking beside it.

What all three need underneath

The same one thing, and it doesn't exist yet: the engine has to say which lead it's on. campaign-live-registry.js:36 already exposes progress(campaignId, account, patch) and the API already ships it as liveProgress {selecting, done, total} — but campaign-worker.js only calls register and unregister, nothing in between. Follower Growth is the only caller (campaign-runtime.js:332). One call per lead in the send loop, plus mapping liveProgress → currentAction in _buildCloudActiveStatus, and all three of these light up.

Introducing needs one more thing: intros fire inside the monitor sweep, so the engine currently has no way to say “introducing” as distinct from “checking”. That's a real phase to add, not just a label.
