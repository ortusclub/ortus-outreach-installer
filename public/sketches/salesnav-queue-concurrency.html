Pause, promote & run-in-parallel

Two things Sam flagged: (1) pausing the running scrape should let the queued one start — today you have to Stop it. (2) In the cloud we want more than one scrape running at a time. Here's how both would look.

01

Pausing should promote the next in line

Right now Pause just freezes the slot — the queue waits behind a campaign that isn't doing anything. Only Stop frees the slot. The fix: a paused campaign releases its run-slot, the next queued one starts, and the paused one drops back into the queue to resume when a slot frees.
Today — pause blocks the queue
1REZ_MIL_I is running. VON_LON_III is #1 in the queue.
2You hit Pause on REZ_MIL_I.
3The slot stays occupied by the paused run. Queue stuck
4VON_LON_III never starts — you must Stop REZ_MIL_I entirely (losing its place) to unblock it.
Proposed — pause = release slot
1REZ_MIL_I is running. VON_LON_III is #1 in the queue.
2You hit Pause on REZ_MIL_I.
3REZ_MIL_I releases its slot & drops to the queue, keeping its progress. Auto-promote
4VON_LON_III starts immediately. REZ_MIL_I resumes from 26% when a slot next frees.

02

Run more than one at a time (cloud)

On a laptop, one scrape at a time is the safe ceiling — each one drives GoLogin browsers that eat CPU/RAM. In the cloud each run gets its own worker, so we can lift the ceiling. A single concurrency dial governs how many run-slots exist; the queue fills them automatically.

The one rule that ties both together There is exactly one knob — run slots. Pause frees a slot, Stop frees a slot, and finishing frees a slot; the queue immediately fills any free slot in order. On a laptop slots = 1 (today's behaviour, minus the pause bug). In the cloud, slots = whatever we set. Same engine, one number.
