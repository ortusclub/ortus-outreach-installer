3 · Tab bar Counter chip alternatives
Current tab strip: each tab has a hairline pill (0) next to its name. Visual: 7 pills competing for attention, most showing 0. Slowness: separate issue — counters are derived from DOM nodes (dashUpdateCounts, app.js:8715) and only update when dashRefreshAll fires. We can fix that with an optimistic local update + a debounced reconcile. Visual fixes are below.

3A · RecommendedBare number · no pill border
Drop the pill border around each count. Number sits inline next to the label, lighter and quieter. Active tab's count goes gold. Pro: calmer strip, fewer visual elements. Con: very subtly de-emphasizes counts (probably the right call when most are 0).
3BHide zeros · gold when non-zero
Only show the number when there's something. Empty tabs read as plain labels. Pro: very clean — the strip lights up only when there's actually work in a bucket. Con: labels visibly shift width when a count appears/disappears; could be jumpy if counts change while you watch.
3CCount on active tab only
Numbers only show on the currently-selected tab. Inactive tabs are plain labels. Pro: least visual noise. Con: you lose at-a-glance "is there anything in Queued right now?" — you have to click in.
3DLabel · count (separator dot)
No pill, no chip — just LABEL · N like a breadcrumb. Pro: reads as one tight unit per tab. Con: the dots compete with the section's · separators elsewhere in the UI.

About the "slow updating" complaint

That's not a CSS problem — it's a refresh cadence problem. The tab counters are derived from DOM nodes by dashUpdateCounts() (app.js:8715) and only re-run when one of the panel refresh functions fires (refreshActiveCampaign, refreshDashboardQueue, the past-list refresh, etc.). If a campaign finishes and the past list hasn't re-fetched yet, the count stays stale.

Fix path (independent of which sketch you pick): after any state-changing action (start, stop, queue add/remove, history append), tell the dashboard to optimistically bump the affected counter immediately, then reconcile with the next full refresh. That removes the perceived lag without changing how counts are computed.
