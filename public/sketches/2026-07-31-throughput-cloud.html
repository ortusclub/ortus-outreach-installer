Throughput · what section 4 should say for a CLOUD campaign

Two settings live in this panel. Daily limit already works on the VM — it is sent to the engine and enforced per account per day. Parallel accounts is not sent at all: the wizard puts it in the request body and the server never reads it. The duration estimate is also local-only — it is computed from “~100 connections/hr (2 parallel)”, which does not describe the VM. Three ways to resolve that, below.

A · Honest cloud panel RECOMMENDED

Parallel accounts is hidden when “Run in cloud” is on, because it does nothing there. The headline forecast switches from a wall-clock guess to the constraint that actually bounds a VM campaign: daily limit × accounts. No new engine work.

Pacing
Cloud campaigns are paced by the engine. Each account is worked by the VM, and the shared account lock keeps a LinkedIn account to one action at a time across the whole fleet — so your accounts already run in parallel.

There is no per-campaign browser count to set here: that knob exists locally because your Mac's RAM is the limit. On the VM it isn't.
B · Keep the knob, fleet-wide WHAT YOU ASKED FOR

The control stays and is wired through to the engine. It has to be enforced across all pods, not per pod — so the honest label is “accounts at a time, fleet-wide”. Note the direction of travel: the engine already runs accounts concurrently, so this can only ever slow a campaign down. Needs engine work + a deploy.
